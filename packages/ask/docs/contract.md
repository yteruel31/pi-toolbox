# `ask_user` contract

## Tool input

```ts
interface AskUserInput {
  title?: string;
  questions: Array<{
    id: string;
    label?: string;
    prompt: string;
    type?: "single" | "multi" | "preview"; // default: single
    required?: boolean;                       // advisory only
    options: Array<{
      value: string;                          // stable canonical value
      label: string;
      description?: string;
      preview?: string;
      recommended?: boolean;                  // presentation only
    }>;
  }>;
}
```

`questions` and each public `options` array must be non-empty. Question ids are unique after trimming; option values are unique within their question. Ids, prompts, values, labels, and supplied preview text must be non-blank after trimming. Terminal control characters are removed before values are validated, rendered, persisted, or included in notifications. A missing option label can be derived from its value by argument preparation before Pi validates the public schema. `preview` questions require non-blank preview text on every option. Fields outside the documented shape have no contract semantics and must not be used.

Every public question gets a final **Type your own** row in the TUI. `/answer` extraction may internally create a freeform-only question with `freeform: true` and no options; that field is not accepted by the public tool schema.

## Tool output

Every execution returns exactly one text content block and structured details:

```ts
interface AskUserResult {
  content: [{ type: "text"; text: string }];
  details: {
    title?: string;
    cancelled: boolean;
    mode: "submit" | "elaborate";
    error?: {
      kind: "invalid_input";
      issues: Array<{ path: string; message: string }>;
    };
    questions: Array<{
      id: string;
      label: string;
      prompt: string;
      type: "single" | "multi" | "preview";
      presentedType?: "single" | "multi" | "preview";
    }>;
    answers: Record<string, {
      values: string[];
      labels: string[];
      indices: number[];       // 1-based row indices
      customText?: string;
      note?: string;           // question note
      optionNotes?: Record<string, string>; // canonical option value -> note
    }>;
    continuation?: {
      strategy: "refine_only";
      affectedQuestionIds: string[];
      preservedAnswers: Record<string, AskAnswer>;
      questionStates: Record<string, {
        status: "answered" | "needs_clarification" | "unanswered";
      }>;
    };
    elaboration?: {
      instruction: string;
      nextAction: "clarify" | "clarify_then_reask";
      items: Array<{
        target: { kind: "question" } | { kind: "option"; optionValue: string };
        question: QuestionMetadata & { options: AskOption[] };
        option?: AskOption;
        selected?: boolean;
        answered: boolean;
        answer?: AskAnswer;
        note: string;
      }>;
    };
  };
}
```

Answer arrays remain arrays for single-select questions. Declared multi-select answers are serialized in declared option order; selected custom text follows them at `options.length + 1`. `values`, `labels`, and `indices` are positional. Question-note-only submission creates an answer with empty arrays and its `note`. Submit includes option notes only for selected declared options. All dictionaries keyed by user-controlled question ids or option values are prototype-free and safely support `__proto__`, `constructor`, and `prototype`.

The agent-facing text is generated by one canonical formatter for tool results and `/answer`, replay, and recovery user messages. It names every canonical question id and includes each selected label, stable value, 1-based index, custom text, question note, and selected option note. It therefore carries note-only submissions without relying on TUI transcript rendering. Agent-facing text is bounded to Pi's standard 50KB/2,000-line tool-output budget; when truncated, the complete structured answers remain in `details`.

## Submission and interaction behavior

`required` does not block submission, and unanswered questions are valid. Review displays all selections without a hidden item cap. Option notes are joined to selections by canonical value and index, never by label.

`presentSingleAsMulti` changes presentation only. The requested `type` remains intact and a different final presentation is reported as `presentedType`. The default `t` action toggles presentation. A multi-to-single change that would drop selections requires the same type action twice; any other action or navigation disarms it.

Numeric Review actions can require confirmation. Their pending state survives Review cursor movement, changes to the newly pressed numeric shortcut, and clears when Review is left.

Inline custom and note editors preserve `@` completion. While autocomplete is visible, Enter and Esc belong to autocomplete. Otherwise configured submit/save commits the editor, and configured close saves the current draft before returning to the ask flow. A whole-flow dismiss does not save the active editor draft. A committed freeform-only answer remains rendered after the editor closes. Footer and editor hints use live configured bindings.

Dirty dismiss/cancel is explicit when configured. No unanswered or recommended option is inferred as approval. Remote submissions use canonical ids and values only.

## Elaborate mode

Elaborate mode preserves committed answers and emits full note-targeted items. `continuation.affectedQuestionIds` identifies only questions needing clarification, `preservedAnswers` carries unaffected answers, and `questionStates` records every question. The agent should answer the clarification directly and re-ask only affected unresolved questions.

## Validation errors

Semantic normalization failures return:

- `cancelled: true`
- `error.kind: "invalid_input"`
- issue paths/messages
- text beginning `Invalid ask_user payload:`

Pi handles structural schema failures before `execute`. Invalid input is not persisted as a valid form.

## Replay and recovery

- `/answer` extracts the latest completed assistant text, persists the independent form, and opens it.
- `/answer:again` replays the latest `answer`/`answer:again` payload on the active branch.
- `/ask:replay` replays the latest real tool payload on the active branch.
- Replay never resolves an interrupted original tool call; a successful replay is sent as a new canonical user message.

Automatic interrupted-tool recovery runs only for Pi session-start reasons `startup`, `resume`, and `fork`. Reload recovery is intentionally out of scope. Recovery considers only the active branch and unresolved `ask_user` tool calls. It validates a matching persisted payload first, falls back to the original tool-call arguments when persisted params are invalid, and writes a dismissal marker after closing. If neither payload is recoverable, it writes an `invalid_payload` dismissal marker before notifying, so subsequent starts do not repeatedly reopen the form.

## Non-TUI modes

The rich flow is available only when `ctx.mode === "tui"`. Print, JSON, and RPC tool execution does not invoke `ui.custom`. It returns `cancelled: true`, empty prototype-safe answers, normalized question metadata, and text beginning:

`Needs user input: ask_user requires interactive TUI mode.`

The text then lists each pending question and each declared `1-based index. label (stable-value)` choice. No answer or cancellation is inferred from the absence of a TUI.
